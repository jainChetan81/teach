What actually survives

Lesson 0002 · ~25 min · completes hdr-2 · feeds capstone ps-1

Why this lesson

Lesson 0001 gave you the wow: close the terminal, the agent keeps working. This lesson takes the wow apart. "Persistent" is not one thing in herdr — it's five different mechanisms, and each one survives a different kind of death. The capstone asks you to rebuild this for t3code, and you can't rebuild what you can't name. By the end you'll be able to answer, for any disaster: what comes back, and what's gone forever?

Phase 1 — Look at your own machine

You already have herdr running. Everything below is read-only. Run each line, look at the output, then read the note under it.

What you should have noticed in session.json: workspaces, tabs, panes, working directories, layout, focus. That's furniture. There is no terminal output in there, no process, no agent memory. The file describes the shape of your session, never its life.

Phase 2 — The survival ladder

Five rungs. Each one survives a bigger disaster than the last, and each one gives you back less. Read top to bottom.

  1. Client dies keeps everything

    You close the terminal window, your SSH drops, your laptop lid shuts. The client was only a view. The server never noticed. Nothing is restored because nothing stopped. This is ctrl+b q done rudely.

  2. Detach on purpose keeps everything

    ctrl+b q. Same mechanism as rung 1, done politely. Panes, shells, agents and processes keep running. Herdr calls this live persistence, and it is the only rung where the word "persist" means "never stopped".

  3. Server restarts keeps the furniture only

    You reboot, or run herdr server stop. Now herdr rebuilds from session.json: your workspaces, tabs, panes, working directories, layout and focus all come back. But every pane is a brand new shell sitting in the old folder. Your build, your agent, your half-finished command: gone. This is snapshot restore, and it is reconstruction, not survival.

  4. Screen history replay keeps the text, not the process

    An experimental, off-by-default feature that also restores recent terminal contents after a server restart, stored in session-history.json. It's off by default on purpose: your scrollback is full of secrets, tokens and keys, and this writes them to a plain file. You get a photograph of what the pane said, not the thing that was saying it.

  5. Native agent resume keeps the conversation

    The clever one. Supported agents (Claude Code, Copilot and friends, via herdr integration install <agent>) hand herdr an official session reference — the agent's own id for your conversation. After a restart herdr asks the agent to resume that conversation. Herdr isn't preserving the agent's memory; it's remembering the receipt and asking the agent to fetch its own. Needs a minimum integration version per agent.

And one special case that doesn't fit the ladder: live handoff (herdr update --handoff, also experimental). When herdr updates itself, it tries to pass the running panes to the replacement server so the processes keep running through the swap. It's the only path where a server dies and rung-2 survival still holds.

DISASTER WHAT COMES BACK ───────────────────────────────────────────────────── client closes → everything (nothing stopped) detach ctrl+b q → everything (nothing stopped) server restart → shape only ← session.json + history replay → shape + old text ← session-history.json (off) + agent integration → shape + the conversation ← agent's own store herdr self-update → everything, if --handoff works
Optional experiment (only when nothing important is running): run herdr server stop, then herdr. Watch your layout come back perfectly and your processes not come back at all. Feeling rung 3 once is worth more than reading it five times.

Phase 3 — The one sentence, and the capstone question

Herdr keeps processes alive by never stopping them. Everything else it offers is reconstruction from notes. That one sentence is the finding you carry into the capstone.

Now hold this next to t3code. t3code has no long-lived PTY to protect — it stores the session (messages, events) in SQLite and re-renders it in a browser. In ladder terms, t3code is permanently living at rungs 4 and 5: it always has the transcript, it always resumes the conversation, and it never has your running shell.

The question to hold, unanswered, until ps-1

For your portable session — the one you carry from Mac to phone to VPS — do you need the running process to survive, or only the conversation? Herdr's answer is "the process, obviously". t3code's answer is "the conversation, obviously". They are both right about different jobs. Write your answer down when you get to ps-1; it decides your whole design.
