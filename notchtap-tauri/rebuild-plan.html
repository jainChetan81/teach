NotchTap rebuild plan

Fourteen logged issues, four independent code surveys, one order of work. Written 19 August 2026.

The one sentence

The visual states are not broken one by one. There is no state machine holding them together, so they can contradict each other, and most of the fourteen issues are what that looks like from the outside.

What the survey actually found

Four read-only agents read the live code. Three checked whether the teaching pages still told the truth. One mapped every visual state, timer, and size. The fourth one changed the shape of this plan.

Finding 1: there is no state machine. There are eleven booleans.

One file, src/hooks/useExitChoreography.ts, takes three inputs and returns eleven separate true-or-false values. StatusRailCard.tsx then glues eight of them into one string of CSS class names and hands it to the browser.

card-assembly | priority | expanded | promoting | hovered | bare | exiting | exit-to-bare

Nothing stops two of those from being on at once when they should not be. The rules that keep them apart are written as comments. One comment says "promoting and exiting never happen together", and that promise holds only because a particular line sits in a particular place. Move that line and the promise silently breaks, with no error.

This is the root of the whole track. Every other item below is downstream of it.

Finding 2: three different things are all called "notch"

NameWhere it comes fromWhat it means
data-notchtap-modeHardware detection at startupDoes this Mac physically have a notch?
restingStateA setting the user picksAt rest, hide completely or show a bar?
bareComputed from the settingDraw nothing right now.

They are independent. You can have "notch" in one and "notch" in another and mean two unrelated things. The Rust hover code reads the first and ignores the second entirely. In App.tsx the word mode is even used for two different values in the same file.

Finding 3: a comment describing CSS that was never written

The idle face sits inside <div class="rest-cluster">. Above it is a seven-line comment explaining how .rest-cluster is positioned and calling the shipped rule "authoritative".

There is no .rest-cluster rule. Anywhere. The string appears in exactly one file in the whole repository, and that file is the one that uses it.

So the wrapper falls into whatever grid cell is free, which is the cell the right flank already occupies. That is issue issue 13, and it was never an alignment problem.

Finding 4: the agent board churn has three stacked causes

  1. Rust decides whether to send an update by comparing the whole session, including the summary text. Every tool call rewrites the summary. So every tool call sends an update.
  2. The board runs its own once-a-second clock whenever any session is under a minute old in its current state. Every state change resets that age to zero. During real work the fast clock effectively never stops.
  3. Every row is marked to animate its position, so the animation library re-measures every row on every one of those renders.

Any one of these alone would be fine. Together they redraw a busy list many times a second.

Finding 5: the idle size is 370 by 32, and the number is written three times

200 pixels of cutout, plus 85 pixels of flank on each side. The 85 is a floor: the flank refuses to be narrower even when it holds nothing. That is issue issue 1 and issue issue 7 in one number.

The 85 lives in two CSS rules and one Rust constant, kept equal by hand. Same for the 200 and the 32. Change one and the app's mouse-tracking and its drawing disagree.

Finding 6: dead code that looks alive

  • The news panel is fully built and wired to a permanently empty list. It renders nothing, ever.
  • One condition in App.tsx can never be true, and a comment in another file defends it against a version of App.tsx that no longer exists.
  • A comment describes "eq bars" in the rest state. There are no eq bars.
  • Eight hook files were moved to a new folder and every single caller still points at the old address through a forwarding file.

How much of this is a rewrite? Less than it feels like.

"Re-architect the whole application" is the wrong size. Here is the honest split, from the survey.

LayerVerdict
The Rust backend: queue, pollers, HTTP server, config, history, settingsLeave it alone. It does not know the overlay exists. Roughly ten thousand lines that this plan does not touch.
The message wiring: seven events in, fifteen commands out, the permission filesLeave it alone. Verified sound, and deliberately locked down.
The overlay's state layer: four filesThis is the rebuild. Eleven booleans become one state machine. Everything else follows from it.
The overlay's components and CSSRework, not rewrite. They mostly render fine; they are fed contradictory state.
The shared size constants, duplicated by hand across Rust and CSSConsolidate. Small, mechanical, guarded by existing tests.

So: one layer is genuinely wrong and needs replacing. The rest is downstream of it, or untouched. That is a rebuild of the state layer, not of the application.

The order of work

The rule for this plan

Each stage ends with the app running and the tests green. No stage depends on a later stage. If you stop after any stage, what you have is better than what you started with.

Steps 13 and 14 — one state machine

The centrepiece. Replace the eleven booleans with one value that can only ever be one thing at a time.

In plain terms: instead of eight separate switches that might disagree, one dial with named positions. The compiler then refuses to let you build a position that does not exist, which is the whole point.

#DoWhy
1.1Write down every combination of the eight class names that the app can actually produce today. Do it on paper first.You cannot replace a machine you have not written down. Expect to find combinations nobody intended.
1.2Turn that list into one named type with one case per real state.This is the moment the contradictions become impossible rather than merely unlikely.
1.3Rewrite useExitChoreography to return that one value instead of eleven.Every consumer gets simpler for free.
1.4Rewrite the class-name assembly as a plain lookup from state to class.The string stops being derived and starts being declared.
1.5Delete the comments that were holding the invariants. The type holds them now.A comment that is enforced by the compiler is noise.

Step 16 — three tiers, not one surface

The rule, decided 19 August 2026

Resting is calm. Hovered is live. Taking over the screen is rare and earned.

Right now all three are the same surface, so a tool call and a finished session get the same treatment. Splitting them is the fix for the churn, and it is a design decision, not a performance one.

TierShowsUpdates
RestingAlmost nothing. Idle says "Idle". Working says something equally short and stable.Only when the tier itself changes. Never on a tool call.
HoveredThe live detail. What is running, what just finished, which files.Freely. This is where movement belongs, because you asked for it by pointing at it.
PromotedTakes over the screen and animates in. This is the only tier that may carry actions.Only on: session finished, needs your permission, needs your input, or failed.

This is the reference app's pattern, and it removes the churn as a side effect. Constant redrawing stops being a problem the moment it only happens while you are deliberately looking at it.

The buttons are the one thing NotchTap cannot do today

Everything else in these screenshots is drawing. The footer is not. Those two buttons act: one opens an editor at the right place, one dismisses the card. NotchTap's overlay window has no permission to call Rust at all. Its permission file grants exactly two things, and both of them are "listen for messages". Zero commands. The build script makes that deny-by-default on purpose.

So the overlay cannot have a button in the way a web page has a button. NotchTap already works around this for its icon strip: the click handler in React is a deliberate empty function (StatusRailCard.tsx:728), and the real click is caught natively in Rust by a system-wide mouse monitor that maps screen coordinates to a target (src-tauri/src/click.rs). Rust decides, then tells the UI what happened.

That is not a bug and it is not the wrong choice. It is a security position: a window with no way to call in cannot be tricked into calling in. But it means every action you want in the overlay costs a native hit-test rectangle, kept in agreement with a CSS rule by hand. Know that price before designing a panel with buttons on it.

This is exactly what steps 8, 9 and 10 teach. Learn the boundary first, then design against it.

The thing to copy is not the look. It is that the resting pill never changes shape.

Idle and Working are the same pill, the same height, the same position. One word changes and a timer appears on the right. Nothing grows, nothing reflows, nothing slides. The eye has nothing to catch on.

Then hover, and the panel that opens repeats that pill unchanged as its own header. So the thing you were looking at stays exactly where it was and the detail arrives underneath it. That is why it does not feel disruptive: the anchor never moves.

What this plan does not do

  • It does not redesign how the app looks. It makes the states honest first, because you cannot judge a design that contradicts itself.
  • It does not touch the Rust backend: the queue, the pollers, the HTTP server, the config. None of that knows the overlay exists.
  • It does not touch the settings window, except to check the one preview that borrows the overlay's card.

Things that will break loudly, and should

Several tests exist for the sole purpose of catching exactly the kind of change this plan makes. They are not obstacles. They are the reason this is safe.

  • A test that checks the icon spacing in CSS matches the icon spacing in Rust.
  • A test that checks every animation duration in JavaScript matches its twin in CSS.
  • A test that checks the overlay's card styles are not duplicated in the settings window.
  • A Rust test that checks the hit-test rectangle constants match the named style constants.
  • Component tests that pin exact CSS selector strings and exact motion values.

When one of these fails, read what it was protecting before you update it. That is the message the last person left for you.

The idea underneath both answers

What you show and what you interrupt with are two different decisions. This app treats them as one, so the only way to make a tool call visible is to make it disruptive. Separate them and both problems dissolve: the detail can be as busy as it likes, because it only exists while you are pointing at it.
