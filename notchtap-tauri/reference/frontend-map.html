NotchTap frontend map

The smallest useful model of the real application. Hooks live in src/hooks/, shared helpers in src/lib/.

Warning: the hooks moved, the imports did not

The hook files really do sit in src/hooks/. But not one line of overlay code imports them from there. Every caller still writes from "./useSlotState", and src/useSlotState.ts is a one-line forwarding file left behind by the move.

What this costs you when hunting a bug: searching for hooks/useSlotState finds the forwarding file and nothing else. Searching for "./useSlotState" finds every real caller. Search for the hook name, not its path.

src/lib/ is the opposite: that move finished, and every import points at the real path. Two moves, one done, one abandoned halfway. This is what an unfinished refactor looks like from the inside.

The main idea

The frontend renders a state machine owned mostly by Rust. React receives state, chooses a surface, and turns that surface into HTML, CSS, and motion.

The complete path

external input ↓ Rust core ↓ Tauri event carrying JSON React custom hook ↓ App.tsx and components ↓ CSS and Motion ↓ macOS webview pixels

You do not need all of Rust to fix the frontend. Start at the custom hook. Move one box left only when the value arriving there is wrong.

Two frontends live in one app

WindowEntry pathDirection
Overlayindex.html → src/main.tsx → App.tsxRust events enter. The UI renders them.
Settingssettings.html → src/settings/main.tsx → SettingsApp.tsxThe UI invokes approved Rust commands.

Vite builds both entries. Tauri places each build inside a separate webview. The overlay stays receive-only. The settings window can invoke a fixed command list.

The split is not perfectly clean. The settings window's Appearance section renders StatusRailCard as a live preview, and pulls in the overlay's stylesheet to do it. So the overlay's root card component has two parents in two different windows. Change it and check both.

Card anatomy: shape states versus attachments

Two different things get confused here. A shape state is how big the card is. An attachment is a piece that mounts onto it depending on what is showing. Four shape states does not mean four possible layouts.

PieceWhat it isWhere it lives
The card bodyThe main surface. Its shape is the state. See the corrected list below the table: there is no class called showing.StatusRailCard.tsx
Below blockA whole extra panel that mounts under the card when a tab is summoned. Agent sessions get one, news stories get one, in theory. See the correction below: the news one is wired to an empty list and renders nothing today.TabBelowBlock.tsx, which picks AgentBelowBlock or NewsBelowBlock
Countdown stripA thin bar at the floor of a showing notification. It counts down how long the card stays, and its segments double as the queue position.TtlBar.tsx, mounted by NotificationBody.tsx
Position barThe "item 2 of 5" strip at the floor of a below block.PositionBar.tsx, mounted by both below blocks
Icon stripThe row of source icons along the top.IconStrip.tsx

So a bar along the bottom is not a fifth mode. On a notification it is the countdown strip. On the agent board it is the position bar telling you which session you are looking at. Same place on screen, different component, different meaning.

Three corrections to the table above

There is no "showing" state. Search the CSS for .showing and you get nothing. The real shape axis is idle, low, medium, high: when a card is showing, the class is the notification's priority, not the word "showing". On top of that sit the modifiers bare, expanded, hovered, promoting, exiting, and exit-to-bare. The last two own the exit geometry and were missing from this page entirely, which matters because exit bugs are the ones you have been seeing.

The two bars are the same CSS. The page said "different component, different meaning", which is true, and then implied they look different in the inspector, which is false. PositionBar.tsx renders <div class="ttl-bar"> with ttl-fill and ttl-seg children, byte-for-byte the classes TtlBar.tsx uses. It reuses them on purpose, to add no new CSS. So opening the inspector and seeing .ttl-bar tells you nothing about which component drew it. You have to check the React tree.

The news below block never renders. TabBelowBlock.tsx holds a constant empty array and passes it in, and NewsBelowBlock returns nothing for an empty list. The component is fully built and completely dead. Selecting the news tab falls through to the ambient idle peek instead. Do not debug it as if it were live.

Worth noticing: the below block is already a slot. One shell, different content plugged in depending on the tab. That is the shape a bigger restructure would extend, not invent.

One event, end to end

Use slot-state as the first trace.

  1. The Rust engine decides whether the slot is empty or showing a notification.
  2. Rust emits a JSON payload named slot-state.
  3. hooks/useSlotState.ts listens for that event.
  4. The hook validates every field before it updates React state.
  5. App.tsx reads the state and passes it to StatusRailCard.
  6. StatusRailCard derives classes, content, and the active below-block.
  7. CSS and Motion turn those classes and elements into the visible card.

Why the validator matters

Tauri events carry JSON and have no shared TypeScript type at runtime. The hook treats the payload as unknown. A malformed payload becomes a safe empty state.

How to locate a UI defect

  1. Write the expected and actual visual states.
  2. Find the final DOM element in the web inspector.
  3. Find the component that produced that element.
  4. Find the prop or hook value that chose its state.
  5. Stop when you find the first wrong value.
  6. Write a failing test at that boundary.
  7. Change the smallest owner and verify on hardware.

A CSS symptom can start in Rust. A missing card can start in a TypeScript validator. A jumping animation can start with two React children mounted at once. Follow the value.

The first retrieval check

A notification has the correct text in useSlotState, but its manifest opens at the wrong time. Where do you look next?

Show the answer

Inspect the component prop and render condition. The wire value is already correct, so follow it forward into rendering.
