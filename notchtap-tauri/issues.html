NotchTap issue log

The UI problems you actually see, each with what you expected, what happened, and how to make it happen again. This page is the deliverable for step 4 and the source of every fix in modules 2 and 4.

How this page differs from the idea log

ideas.html holds opinions about how the app should be built. This page holds defects: something looks or behaves wrong, and it can be demonstrated. An issue needs four things before it can be fixed — expected, actual, trigger, and evidence. Anything missing one of those is marked needs detail and cannot start yet.

Read this before trusting anything below

These observations come from an installed build made before the big cleanup. Proof: the screenshots show a music-note icon and a cloud icon in the strip. Those two tabs no longer exist in the code — the tab list is now Agent, Football, News only.

That matters for two of the reports specifically, because the cleanup changed the exact code they touch:

  • Hover width is derived from the number of visible icons (src-tauri/src/hover.rs:69, hovered_right_flank_width). Fewer icons means a different hover zone. The edge-hover report must be re-tested.
  • The idle hover peek lost its weather branch, so the idle surface itself is not the one in the screenshot.

Next step: rebuild and reinstall, then re-check each item. Ones that survive are real. This is not a delay, it is what stops us fixing a bug that is already gone.

Known good: the news surface

Your own verdict while watching it live: the animation looks nice, the UI looks clean, and it shows enough information without clutter. Room to improve, but nothing wrong.

This is more useful than it sounds. It gives every other fix a target inside your own app: when the idle bar or the agent card feels wrong, the question becomes "why does this not feel like the news card?" — a comparison you can actually make, instead of an abstract judgement. Keep this entry updated as surfaces reach the same bar.

Status: the hunt is closed, on purpose

Fourteen issues are enough. The states themselves are being rebuilt on both sides, Rust and React, so most of what is listed here will be rewritten rather than patched. Finding a fifteenth issue in code that is about to be replaced buys nothing.

This page now has one job: it is the acceptance list for the rebuild. When a state is rebuilt, the matching issue here has to come out true. Do not add more unless something new and surprising shows up while building.

Issue 5. Agent card churns while tools run confirmed in code

ExpectedA calm surface that tells you an agent is working, without redrawing on every tool call.
ActualContent changes constantly as the agent edits, greps, runs commands. Reads as restless.
TriggerRun an agent that uses many tools in a row and watch the agent tab.
Diagnosis, confirmedThree causes stacked on each other. One. Rust decides whether to push an update by comparing the whole session including summary and details (agents/model.rs:403). Every Claude Code tool call rewrites both (providers/claude_code.rs:133), so every tool call pushes a fresh snapshot to React. Two. On top of that, the board runs its own clock at one tick per second whenever any session has been in its state for under a minute (AgentBoard.tsx:43), and every state change resets that clock (registry.rs:281), so during real work the fast tick almost never stops. Three. Every row carries layout="position" (AgentBoard.tsx:263), which makes the animation library re-measure every row on every one of those renders.
AlsoRows genuinely reorder. Rust sorts by urgency (model.rs:122), and "waiting for permission" ranks 0 while "working" ranks 5. Approving a permission moves a session from top to near-bottom, animated. That is correct behaviour that reads as churn.
Evidencent4-01 and nt4-03 show two consecutive states, one second apart, differing only in the path chip.
MissingWhich behaviour you want: fewer updates, the same updates but animated softly, or a summary that only changes on meaningful events. This is a design decision, not a bug fix, until you pick one.
RelatedTouches idea 6 (fire-and-forget events versus persistent state). Worth reading that entry before deciding.

Issue 7. Idle state is physically too big ready to pin down

ExpectedThe idle bar takes only as much room as it needs.
ActualIt occupies noticeably more width and height than its contents justify.
TriggerLet the app go idle and compare the bar against the notch cutout.
EvidenceVisible in nt4-02, and closely tied to issue 1: the empty right half is part of the excess size.
The number, confirmedIdle is 370px wide by 32px tall. That is a 200px cutout plus 85px of flank on each side. The 85 is a floor: the flank never gets narrower than that even when it holds nothing. It is written by hand in three places that must move together — card-chrome.css:73, card-chrome.css:259, and hover.rs:25. The 200 and 32 are written in three places too (App.tsx:21, hover.rs:29, and the CSS fallbacks).
Try this first, it needs no codeOpen the settings panel, Appearance section, and lower the card scale. Valid range is 0.8 to 1.4. The change applies instantly with no relaunch, because set_appearance broadcasts to the overlay rather than restarting.
Then decideIf a lower scale fixes it, this was a settings issue, not a defect. If the proportions still look wrong at 0.8, the idle surface has its own sizing problem and becomes a real fix. Report which.

Issue 8. The card does not follow you to another display deferred, on purpose

ExpectedWhichever screen you are working on, the card appears there.
ActualIt stays on one display. Work on another monitor and you never see the notification.
TriggerMove to a second display, then trigger any notification.
OwnerRust, window placement. position_top_center and the cutout-anchored path in src-tauri/src/lib.rs (around lines 1259 and 1775).
Diagnosis, already confirmedTwo different things get confused here. Spaces are handled: the window is created with CanJoinAllSpaces (lib.rs:1242), so it shows on every virtual desktop of its own display, and Stationary keeps it from sliding around during a Space switch. Displays are not handled: the window is positioned once, against whichever monitor was current at setup, and nothing repositions it afterwards. A search for a screen-change listener finds none.
What a fix needsSomething must notice "the active display changed" and re-run the placement. That means a native screen-change or focus observer on the Rust side. Not a React fix, and not a small one.
Decided, 19 Aug 2026Not now. One display only. The fix needs a native screen-change observer on the Rust side and a product answer about which display wins, and neither is worth spending before the states themselves are honest. Revisit after the rebuild. Nothing else in the plan depends on it.

Issue 10. You cannot tell whether it is silenced confirmed in code

ExpectedOpen the menu and know, in one glance, whether notifications are being held back right now.
ActualThe answer is there, but it does not read as an answer. The second row says Not Silenced in grey. Grey means "disabled button" everywhere else on a Mac, so it scans as a broken menu item, not as a status line.
TriggerClick the NotchTap icon in the menu bar. nt4-08.
OwnerRust. src-tauri/src/tray.rs, silence_indicator_label (line 63) and build_tray (line 219).
Diagnosis, already confirmedThe status is a real menu item created with enabled = false, so macOS greys it out. There is no separator above or below it, so it sits in the same visual run as the four real actions. There is also no expiry text: when a mute is running, the menu never says until when.
What a fix needsSeparators around the status row, and text that names the state as a state, for example "Silenced until 12:30" or "Notifications on". A checkmark next to the active mute preset would do the same job.

Issue 11. Two silence indicators, set from different places confirmed in code

ExpectedThe moon glyph in the menu bar and the menu's status row always agree.
ActualThey are written by two different code paths, and one of them is skipped at startup.
OwnerRust. src-tauri/src/tray.rs: set_silence_indicators (line 84) writes both; build_tray (line 231) writes only the menu text.
Diagnosis, already confirmedbuild_tray sets the menu label from the boot verdict but never sets the tray title, so the moon is unset until spawn_silence_task runs its first pass (lib.rs:872, after the tray is built at lib.rs:677). Small window, but the two indicators have no single owner.
What a fix needsOne function that writes both, called at boot and on every change. set_silence_indicators already is that function. build_tray just has to call it.

Issue 12. Changing quiet hours does nothing until you restart confirmed in code

ExpectedEdit the silence window in Settings, and the app starts obeying the new window.
ActualNothing changes until you quit and reopen the app.
TriggerSettings, change the silence window, then wait for the new window to begin.
OwnerRust. src-tauri/src/silence.rs and src-tauri/src/lib.rs:351.
Diagnosis, already confirmedSilenceController::new(schedule_enabled, window) is called once at startup. The type has no setter for the schedule at all: its public methods are is_silenced, start_mute, cancel_mute, skip_current_window, next_boundary. Nothing else in the codebase mentions SilenceController outside lib.rs boot and tray.rs. The background timer also sleeps until the old schedule's next boundary, so even a setter would need to wake it.
What a fix needsA setter on the controller, plus a wake signal for the sleeping task, plus something in the settings save path that calls both.

Issue 6. Reference implementation to compare against answered, with screenshots

WhatThe Notch, installed alongside t3code. You rate its behaviour clearly better than NotchTap's.
What it does better, in one lineIt stays quiet by default and reveals on demand.
Resting, nothing runningA pill inside the cutout: one glyph, the word "Idle". Nothing on the right, no reserved empty space. nt4-09.
Resting, one agent workingThe same pill, same size, same place. Animated glyph, the word "Working", elapsed time on the far right. That is all. Tool calls do not move it. nt4-11.
HoveredA panel whose header is that pill, unchanged. Below it: project, session title, model, machine, OS, start time, elapsed, git branch, a progress ring with a percent, a state chip, and a live activity feed of recent commands. nt4-10.
Resting, finishedStill the same pill. Glyph, the word "Done", the final elapsed time. It does not grab you. nt4-13.
Hovered, finishedThe same panel plus a footer bar: a status line, and two buttons, Open in T3 Code and Dismiss. nt4-12.
The one thing we cannot copy yetThose buttons. NotchTap's overlay window has no permission to call Rust at all: two permissions, both "listen", zero commands, enforced by the build script. NotchTap catches its icon-strip clicks natively instead, in src-tauri/src/click.rs, with the React handler left as a deliberate empty function (StatusRailCard.tsx:116). So every action in the overlay costs a hand-maintained hit-test rectangle in Rust. Learn the boundary (steps 8 to 10) before designing anything with buttons on it.
The pattern, namedThree tiers: resting is calm and fixed, hovered is live and detailed, promoted is rare and earned. NotchTap currently collapses all three into one surface that updates constantly.
The detail that makes it workThe resting pill never changes shape. Idle and Working are the same pill; one word changes and a timer appears. And the hovered panel repeats that same pill as its header, so the thing you were looking at does not move when the detail arrives. The anchor stays put.

How to run it and what to look for

Weather and media cannot be switched on

There is no command or setting for them. You deleted both features, so the code, the settings sections, the tabs, and the icons are gone. Turning them back on means reverting that work, which is a decision, not a toggle. The screenshots show them only because that installed build predates the removal.

What you can switch on: football and news. Those are the two content sources that still exist, alongside agents.

Wait for the anti-slop run to finish first

That tool is editing the app right now. Building mid-edit gives you a binary that matches neither the old code nor the new. Let it finish and land, then build.

Step 1 — run the app from source

cd ~/Desktop/code/mac-notification-nudge
just dev

This runs it in dev mode, which is what you want while hunting UI bugs: the web side hot-reloads, so a CSS or React change shows up without a rebuild. Rust changes still need a restart.

Step 2 — turn on the sources you want to see

Open the settings panel. The sections that matter here are Football, News, and Agents. Enabling football or news needs a save, and saving relaunches the app by design.

Step 3 — make notifications appear on demand

The settings panel can send a test notification for any of four sources: football, news, manual, agent. Use that instead of waiting for real events. It is the fastest way to reach the compact and expanded states repeatedly.

Step 5 — record, do not just remember

For anything about motion, a still image cannot show the problem. Use the macOS screen recorder (Shift plus Command plus 5) and keep the clips to a few seconds. Two are needed: the idle hover snap, and the edge hover.
