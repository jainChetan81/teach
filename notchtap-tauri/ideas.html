NotchTap idea log

Every thought, suggestion, and "we should probably…" about the app. Captured when you say it, not when we act on it. Nothing here is a commitment.

How this page works

You say it, I write it down here with a short honest take and a status. Status means: open = not judged yet, ready = we know what it would take, blocked = something must happen first, done = shipped, parked = deliberately not doing it. Nothing gets built from this page without you choosing it.

Open ideas

10. UI as a pure presentation layer may itself be the bug source open

Your words: "the majority of events are triggered by the Rust part. The UI often doesn't know how it's working. It's just a presentation layer and that could be the big reason why a lot of these issues are happening."

  • The idea: the strict Rust-decides/React-renders split is not free. The UI cannot reason about its own state, so timing and animation bugs appear as mysterious behaviour with no local cause.
  • Half true, and the half matters. Interaction state (hover, tab, viewed session) really does round-trip through Rust, and that latency is idea 4's whole point. But the animation bugs you want to fix live in state React does own: the choreography spread across useDelayedSwap, useExitChoreography, and timers inside StatusRailCard (idea 2).
  • My take: right that the architecture is worth re-opening, wrong that Rust ownership is the culprit. Two owners of visual state (Rust for "what", React for "how it moves") is the real shape. Test the hypothesis against real defects before restructuring — that is exactly what module 2 is for.

9. One generated source for commands and capabilities open

Your words: "we don't need the fourth level. What we should have is one JSON where all the commands are, both front and back, and that command can also have capability."

  • The idea: collapse the duplicated command list into one declaration that generates the TypeScript mirror, the capability file, and the Rust allowlist.
  • Layers 1–3 agree with you. They are three copies of one list, and build.rs already generates part of the chain from SETTINGS_COMMANDS. Generating the rest is real, and it is the same fix as idea 1 (generate TS from Rust) widened to permissions.
  • Layer 4 is not the same thing. Layers 1–3 are build-time configuration; layer 4 is a runtime check of which window is calling. No generated file can answer that, because the caller is only known when the call happens. It is 3 lines and one string compare.
  • My take: generate layers 1–3 from one source, keep layer 4. Bundle the decision with ideas 1 and 3, since all three are "one source of truth across the language boundary."

7. Status as one enum instead of parallel booleans open

Your words (2026-08-16): "status should actually be an enum of strings... that alone will track what the current state is."

  • The idea: replace flag-shaped status (paused, playing, etc.) with one string enum naming the current state.
  • What exists today: StatusState is not really booleans — it is a bundle of independent facts (paused, waiting count, agent count, football, news charge, weather, media). Several are true at once, so one enum cannot hold them.
  • The twist: the enum you want already exists one step later: presentationMode() collapses everything into "notification" | "board" | "idle". That IS the single decider.
  • My take: right instinct, wrong layer. Keep status as parallel facts, keep the enum at the mode layer. If anything, more decisions should flow through presentationMode, which connects to idea 5.
  • Refined 2026-08-16: he means it as a general principle for the whole codebase ("in general we should have an enum" for any one-of-several state), not just this spot. Treat it as a design preference to apply wherever a real one-of-several state shows up.

8. Comment noise makes files unreadable open

Your words (2026-08-16): "there are so many unnecessary comments and crap that I can't even understand what's going on."

  • The idea: a cleanup pass that strips or relocates the wall-of-comment blocks (plan numbers, review-wave notes) so the code reads as code.
  • What exists today: nearly every comment is an AI provenance note ("plan 084...", "review fix wave C...") written for a past reviewer, not for you. Some encode real constraints (load order, animation invalidation rules); most are history.
  • My take: legitimate, and it hurts you daily. But a blind strip would delete the few load-bearing ones. Right move: as we touch each file for a real fix, keep constraint comments, delete history comments. Cleanup rides along with fixes, not as its own pass.
  • Confirmed leftovers after the cleanup, found by you while tracing a command. The comment purge missed prose outside // comments: src-tauri/capabilities/settings.json's description field still narrates removals ("the telegram-connector removal dropped…", "the secrets-store removal dropped…") and cites two spec docs that no longer exist, and src-tauri/build.rs still opens with "v5 (V5_TECHNICAL_SPEC.md §2)". Both break your own current-product-only rule. Real, small, worth a follow-up sweep of JSON description fields and doc-comment spec citations.

5. One persistent shell, plugins inside open

Your words (2026-08-15): "a shield, and inside it multiple plugins that each work the way they work; the big structure never moves."

  • The idea: instead of swapping whole top-level surfaces (notification / board / idle), keep one stable shell and let content plugins re-skin the inside. The frame stays put; only the content changes.
  • What exists today: the app swaps three surfaces via presentationMode(). It is a design opinion this app evolved into, not a law. Your model is how a lot of "one persistent widget" apps work.
  • My take: valid restructure direction, and it would simplify the trigger-1 surface-swap. But do not reshape until you understand the current three-surface reality and the exit choreography. The plugin framing also connects to idea 4 and the whole "one funnel out" architecture opinion (NOTES). Revisit after the map is done.
  • Raised again (2nd time), 2026-08-16, unprompted: after reading StatusRailCard he re-derived it as "a rendering engine where we give it what to render and it decides... multiple plugins inside it... any component can be slotted in." Two independent derivations now. Signal is getting stronger.

6. Split command-events from state-events open

Your words (2026-08-15): "an event should come, happen, die. But weather and media player are permanent, remembered. Coding notifications fire and forget."

  • The idea: two kinds of wires. Fire-and-forget ones (a notification arrived → show → forget, maybe append to a history log) and persistent state ones (weather, media player → the current truth, re-sent on change).
  • What exists today: the repo is deliberately all state-sync — every wire re-sends the current truth and dedups with compare-with-last. That is why the weather/player wires re-emit periodically.
  • My take: your split is the correct mental model for how it should feel, and it maps onto real source kinds (news/agent = event-ish, weather/media = state-ish). Worth encoding when we design a future restructure. Keep it parked; it will inform how we read the plugin question, not something to change now.

Your animation focus (stated 2026-08-03)

1. One source of truth for the types on both sides ready

Your words: "a way to unify types between events, Rust and TS."

  • The problem is real and already hurting. The tab identity set is hand-written in six places across two languages. useSlotState.ts hand-mirrors four Rust enums with a comment on each saying "keep in sync by hand."
  • Today's answer is tests, not generation. tabWireParity.test.ts and settings/hookEventParity.test.ts read both files as text and fail CI on drift. That catches the bug; it does not delete the duplication.
  • The real fix has a name: generate the TypeScript from the Rust. tauri-specta (built on specta) is the Tauri-native option and types commands and events, not just structs. ts-rs is the smaller, simpler one that does structs only.
  • My take: the highest-value idea of the four. But it rewrites the top of all seven hooks, so do it once you can navigate them, not before. It also pairs with idea 3, so decide them together.

2. A state manager for queue, timers, priority open

Your words: "a state manager to handle queue, timer priority notification etc."

  • Careful here. The queue, priority ranking, TTL, and preemption already live in Rust (queue.rs, engine.rs). A frontend store holding the same things would create a second source of truth, and disagreements between two owners is exactly how animation bugs breed.
  • But there is a real gap. The frontend choreography state, which Rust does not own, is spread across useDelayedSwap.ts, useExitChoreography.ts, and several one-off timers and refs inside StatusRailCard.tsx. That is genuinely hard to reason about and it is where your animation bugs live.
  • My take: no Redux or Zustand for wire data. Yes to eventually consolidating the choreography into one explicit state machine, so "which visual state am I in, and what is allowed next" has one answer instead of six booleans. Revisit after we have fixed two real bugs by hand, so the machine is designed from evidence.

3. Zod for payload validation open

Your words: "zod for validation."

  • Fair target. useSlotState.ts spends roughly 100 lines on hand-written type guards. A schema would say the same thing in a fraction of that and give you the inferred type for free.
  • Zod is not currently a dependency of the app.
  • The trap: if idea 1 lands first, the schemas could be generated from Rust too, and writing them by hand now means writing them twice.
  • My take: good idea, wrong order. Bundle it into the idea 1 decision.

4. Own click and UI state in the UI, not Rust blocked

Your words: "click and UI state through UI itself not rust."

  • This is the deepest of the four. Hover, tab selection, and the viewed agent session are Rust-owned today for a physical reason: the overlay window is largely click-through, so the webview never receives real pointer events. That is why hover arrives as a message from a native tracking area instead of a CSS :hover rule.
  • So this is not a preference change. Moving it means changing the window's click-through behaviour and hit testing in Rust, then deleting the tracking area. Real work, with a real payoff: interaction state would become instant and local instead of a round trip.
  • My take: keep it. It is the single best motivation for module 3 of the plan, because it is the exact place where "just fix it in React" stops being possible. We should not touch it until you have crossed the boundary once on something smaller.
  • Raised again (2nd time): you predicted the Notch must become clickable for the agents view, and assumed that means granting the overlay invoke permission. It does not — and the app already solved it. See src-tauri/src/click.rs: a native NSEvent monitor watches clicks, decides which icon was hit, and emits tab-selection-changed. The overlay stays receive-only and still responds to clicks. Your instinct about where the app is heading was right; the mechanism is native, not a permission change.
  • Raised a 3rd time, now with evidence, and my take has changed. You argued interaction state (a news slider, hover-to-expand) belongs in the UI, and named the hover behaviour as feeling flaky. The repo backs you up. Two levels have been conflated:
    • Outer boundary (is the cursor over the card at all): Rust must own it. The overlay window is click-through (set_ignore_cursor_events(true)), so the webview receives no pointer events at all. Physics, not preference.
    • Inside the card: the webview does get real events once cursor events are toggled on, and the app already relies on that. AgentBoard.tsx:341 opens its history popover with plain onMouseEnter/onMouseLeave and React state. No Rust round trip. It works.
    The proof that the blanket rule hurts: your exact news-slider example is half-built and dead. NewsBatchHeader.tsx:59 renders real prev/next buttons with real onClick handlers, and NewsBelowBlock.tsx:142 mounts them — but the handlers are "presentational callbacks only" and the file's own comment admits click routing is deferred and unbuilt. Same story for IconStrip's onSelect={noopSelect}. Buttons that look clickable and do nothing.
  • Revised take: the NSEvent monitor was the right call for the icon strip, which sits in the click-through zone. The mistake was promoting "Rust decides" from a boundary rule to a blanket rule, so widgets inside the card also wait on routing nobody built. Proposed split: Rust owns the window boundary and anything that changes app state; React owns interaction inside the card (slider position, hover-to-expand, press feedback). This is now the strongest restructure candidate on this page.
