The two doors

How data crosses the Rust–web boundary in both directions, and why the two windows never use the same door. One sitting, ~25 minutes, no code changes.

Why this lesson

You already found that the Notch and the settings panel are two separate pages that never talk to each other. This lesson names the two mechanisms they use to talk to Rust, and shows the four-layer allowlist that keeps them apart. It is the groundwork for nt-8 and nt-9 on the plan.

1. One boundary, two doors

A Tauri app is one Rust process holding one or more webviews. Web code cannot call Rust functions directly; everything crosses a message boundary. Tauri gives that boundary two doors:

DoorDirectionMechanismWho uses it here
EventsRust → webRust emits a named JSON message; the page listens.The Notch. All seven wires.
CommandsWeb → RustThe page invokes a named Rust function and awaits the result.The settings panel. Fifteen commands.

The design rule this app enforces everywhere: the Notch is receive-only and the settings panel is ask-only. The Notch never invokes. The settings panel never renders live overlay state from events; it asks and receives answers.

2. Door one, seen from the code

You know this door already from lesson 0001: seven listen calls in src/hooks/ and App.tsx. What is new is the permission underneath it. Each window has a capability file that says what it may do. The Notch's is src-tauri/capabilities/default.json, and it is five lines of meaning:

"windows": ["main"],
"permissions": ["core:event:allow-listen", "core:event:allow-unlisten"]

Listen and stop listening. Nothing else. Even if someone later wrote invoke("clear_queue") inside the overlay by mistake, Tauri would refuse it at the boundary, because the main window's capability grants no commands at all.

3. Door two, the command path

Every settings action funnels through one wrapper: settingsInvoke() in src/settings/ipc.ts. It is the only place in the whole frontend that calls Tauri's invoke. The file starts with a typed map of all fifteen commands — name, arguments, result — so a typo'd command name or a wrong payload fails the type check before it ever runs.

A command like save_config_and_relaunch passes through four layers, each of which must agree:

#LayerFileWhat it does
1Typed mirrorsrc/settings/ipc.tsTypes the fifteen commands for TypeScript. Grants nothing.
2Capabilitysrc-tauri/capabilities/settings.jsonGrants the settings window, and only it, permission to call them. It also grants that window core:event:allow-listen and allow-unlisten.
3Allowlist + registrationsrc-tauri/src/settings_commands.rs → build.rs → generate_handler! in lib.rsOne list of fifteen names, asserted by a test, fed to the build and the runtime registry.
4Runtime guardensure_settings_window() in src-tauri/src/settings.rsEach handler re-checks the caller is the settings window. Defense in depth.

Layer 4 exists because layers 1–3 are configuration, and configuration drifts. If a future edit registered a command without the capability opt-in, the handler itself would still refuse the wrong window. Adding or removing a command touches all four layers in one change.

Correction: the build does not catch this. Tests do.

An earlier version of this page said the count assertion "fails the build". It does not. It is a #[cfg(test)] unit test, so it runs under cargo test, never under cargo build. A half-finished edit compiles cleanly and would ship.

And the direction that matters fails open. The code says so itself, in settings_commands.rs:6-10: a command missing from the canonical list "silently becomes callable from the overlay window as well". Forgetting is not a build error. It is a quietly widened permission.

Three tests in src-tauri/src/settings_commands.rs are what actually hold the line: canonical_list_has_the_documented_fifteen_commands (line 73) checks the count, settings_json_permissions_match_exactly (line 95) compares the whole permission set against the command names, and generate_handler_registers_exactly_the_canonical_commands (line 138) reads lib.rs as text and pins the registration list. The count assertion alone is the weakest of the three.

The lesson underneath: when a mistake fails open, a test that must be remembered and run is the only guard you have. Know which of your guards run automatically and which do not.

4. Why the directions differ

This is the nt-9 question, answered once and properly:

  • The Notch listens because Rust owns the truth. Queue, pause, tabs, sessions all live in Rust. The overlay is a projector. A projector that could also change the film would be two sources of truth, and you have already logged where that leads (idea 2).
  • The settings panel invokes because it wants side effects. Save this config. Clear that queue. Send a test notification. Those are requests, and requests need a reply channel — invoke returns a promise with a result or an error, which events do not.
  • Security follows the same split. The receive-only window is the one always on screen; it has no power to misuse. The powerful window is the one you open on purpose, and its power is a fifteen-item list you can read in one screen.

One command breaks the pattern, on purpose

save_config_and_relaunch does not return a result the panel renders. It validates, writes config.toml atomically, then restarts the whole process — the relaunch you guessed correctly in chat. The reply channel is the app coming back up with the new config loaded at boot.

5. Do this now (10 minutes, changes nothing)

  1. Prove the Notch never asks:

    cd ~/Desktop/code/mac-notification-nudge
rg -n 'invoke\(' src --glob '!settings/**' --glob '!*.test.*'

    Only comments saying "no invoke here". The single real caller is src/settings/ipc.ts.

  2. Read both capability files side by side:

    cat src-tauri/capabilities/default.json src-tauri/capabilities/settings.json

    Note which windows they name, and that the overlay one grants listen only.

  3. Find the command-count assertion:

    rg -n 'SETTINGS_COMMANDS.len' src-tauri/src/settings_commands.rs

  4. Say out loud, without looking: the two doors, who uses which, and the four layers a command passes through.

Check yourself

1. Someone adds invoke("skip_current") to the Notch overlay. What happens?

2. A future feature needs the panel to ask Rust a question and show the answer. Which door?

3. You add a brand-new settings command. How many layers must you touch?

Done with this lesson when

You can name both doors, say which window uses which and why, and list the four layers between settingsInvoke() and a running Rust handler.
