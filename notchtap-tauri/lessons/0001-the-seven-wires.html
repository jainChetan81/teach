The seven wires

Where NotchTap's data comes from, where it sits, and what makes an animation start. One sitting, about 20 minutes, no code changes.

Why this is the first thing

You want to fix animations yourself. Nearly every animation bug in this app is really a question about a value that changed at the wrong moment. So before you can fix motion, you need to know which values exist, who sends them, and when. That is this lesson. After it you can read any bug report and say which of three triggers is involved.

1. The rule that makes the app small

The overlay window does not fetch. It does not poll. It does not read files. It holds no database and no store. Rust decides everything and pushes it in.

That means the entire input surface of the UI is a short list of named messages. Seven of them. You can hold seven in your head.

the outside world ↓ Rust decides ↓ one of 7 named events, carrying JSON one React hook per event ↓ useState App.tsx ↓ plain props components → CSS and Motion → pixels

2. The seven

EventAnswers the questionLands in
slot-stateWhich notification is showing?useSlotState.ts
status-stateAre we paused? What is live?useStatusState.ts
agent-stateWhich agents need me?useAgentState.ts
tab-selection-changedWhich tab is selected?useTabSelection.ts
agent-viewed-session-changedWhich session am I looking at?useAgentViewedSession.ts
appearance-changedHow big, how round, how solid?App.tsx
hover-changedIs the cursor on the card?App.tsx

The full table, with the exact Rust line that sends each one, lives in the wire table. Keep that page open while you debug; do not memorise it.

Two things worth noticing now:

  • Every wire runs one way. Rust to overlay. The overlay never asks for anything. Only the settings window is allowed to call into Rust.
  • Hover is a wire too. That surprises most React developers. The cursor position is decided by a native tracking area in Rust, not by a CSS :hover rule, because the window is mostly click-through.

3. Where the data sits

There is no clever state layer. Each hook does the same three things:

const [slot, setSlot] = useState<SlotState>(initialSlotState);   // 1. one useState
useEffect(() => {
  listen<unknown>("slot-state", ({ payload }) =>                 // 2. one listener
    setSlot(isValidSlotState(payload) ? payload : { state: "empty" }));  // 3. validate
}, []);

That is useSlotState.ts, compressed. All seven hooks are the same shape. App.tsx calls them, and from there everything travels down as ordinary props.

Why the validator is not paranoia

A Tauri event arrives as JSON. TypeScript types vanish at runtime, so the payload is typed unknown and checked field by field. A payload that fails any check becomes an empty state, not a half-drawn card. Practical consequence: if Rust adds a new value to an enum and the TypeScript list is not updated, the card silently disappears instead of throwing. When a notification vanishes for no reason, suspect the validator first.

4. When a wire fires

On change only. Rust compares the new value with the last one and stays quiet if they match. There is no per-frame stream and no heartbeat.

So a stuck screen is usually a wire that never fired, not a component that failed to re-render. That single habit will save you hours: before you inspect React, ask whether the event was sent at all.

5. What actually starts an animation

This is the part you came for. In this app, exactly three things start motion.

#TriggerWhat it looks like in code
1A surface swaps. The whole top-level card is replaced.A child mounts or unmounts inside AnimatePresence in App.tsx.
2The content swaps. Same card, different item inside it.A React key changes. swapKey is slot.id while showing, and the string "idle" otherwise.
3A class flips. Same elements, new look.A boolean like hovered or exiting adds a class, and CSS transitions it.

Trigger 1 is decided by one small pure function, presentationMode():

if (slot.state === "showing") return "notification";
if (paused) return "idle";
return sessionCount > 0 ? "board" : "idle";

Three lines decide which surface you see. A notification always wins. Pause quiets everything, the Agent Board included.

Trigger 2 is the one that bites. React unmounts a node when its key changes, so an exit plus an entrance play. If two different notifications share an id, no swap animates. If an id changes when it should not have, the card replays its entrance for no visible reason.

Trigger 3 is where CSS finally does the work, and where durations must match numbers declared in JavaScript.

All the clocks live in one file

src/animationTiming.ts holds every duration and the house easing curve. Some of those constants are locked to a CSS value by a test, so editing one side alone fails the suite deliberately. When an animation feels wrong, retuning a number in that file changes every consumer at once. That is the intended repair, not editing a duration in a stylesheet.

6. Do this now (5 minutes, changes nothing)

  1. Count the input surface yourself:

    cd ~/Desktop/code/mac-notification-nudge
rg -n 'listen<' src --glob '!*.test.*'

    Seven lines. Confirm each one against the table above.

  2. Find the one file where the wires meet:

    rg -n 'use[A-Z][A-Za-z]*State|useTabSelection|useAgentViewedSession' src/App.tsx

  3. Read the three lines of presentationMode:

    rg -n 'export function presentationMode' -A 12 src/lib/presentation.ts

  4. Now say out loud, without looking: the seven wires, and the three animation triggers. Getting five of seven is fine. The point is the retrieval, not the score.

Check yourself

1. The Agent Board appears while the app is paused. Where is the bug?

2. A new notification replaces an old one with no animation at all. First suspect?

3. Rust adds a new source kind. Cards from it never appear. Why?

4. The card is frozen on stale content. What do you check first?
